AC-P2-01 · A token endpoint is an authorization boundary — CORE

Your frontend asks for a room token and supplies roomName and participantName. Which values can the server trust, and what must it decide itself?

A valid room JWT proves that a server signed particular claims. It does not prove that the person calling your token endpoint was entitled to those claims. I would authenticate the application user first, resolve their permitted account and conversation on the server, choose an allowed participant identity, and grant only the required room/media/data capabilities. A display name can remain user supplied, but it must not select another customer's case or grant administrative powers. Signing credentials stay server-side; keeping them there is one control, not the whole authorization design.

I would also authorize agent selection and validate bounded dispatch metadata. The room grant lets a participant connect; it does not grant a model or browser permission to confirm a booking. For an interview failure case, I would submit a valid logged-in user's request naming another account's room, then check that issuance fails before dispatch. This is a proposed frontend exercise. The POC's trusted P2 construction and separate exact confirmation are related examples, not evidence that its console implements the Academy React template.

Does a short token lifetime remove the need to authenticate this endpoint?

No. An attacker can obtain another fresh token while issuance remains open. Token lifetime limits one credential's validity; the issuer still needs application authentication, authorization, bounded admission and a documented revocation/recovery policy.

Can a participant attribute safely contain a role?

It can carry a backend-issued claim if the design prevents the participant from rewriting it and verifies its trusted origin. A mutable self-asserted attribute cannot grant business authority. Prefer a server-side principal binding for consequential operations.

AC-P2-02 · Choose RPC, synchronized state or a durable command — CORE

A browser can call an availability RPC and display a confirmation topic. How would you prevent those convenient realtime APIs from becoming an unsafe booking protocol?

A cold phone transfer forwards the existing SIP caller through the provider, commonly using REFER; it can end the caller's LiveKit session. Bound retained bytes/time, handle malformed/incomplete structures explicitly, and validate the intended schema and domain values rather than merely parsing JSON. Respect the actual ChatChunk structure, including tool calls and other required metadata. Bind emotion or rendering metadata to the response that produced it rather than a mutable shared last value. Choose the latency cost of withholding output deliberately, test chunk-split forbidden patterns and failure paths, and keep sensitive generated reasoning out of logs. Display-only filtering is a separate boundary from audio release.

Is fail-open always wrong on moderation failure?

The policy depends on the product, but it must be explicit and truthful. A parse failure is unknown, not a positive safe verdict. Decide whether to withhold, use a constrained fallback or escalate; test that branch independently.

Can text filtering protect a realtime model from original audio?

Not if that audio has already been sent to the provider. Apply the required protection before that ingress boundary or select another architecture. Similarly, filtering a transcript after synthesis cannot retract published speech.

AC-P2-04 · A dial timeout is not permission to call twice — OPTIONAL / MERGE

Your outbound-call request times out just as the customer's phone starts ringing. How would you design retry, capacity and user-visible status?

I would retain the original authorized dial intent, immutable destination, local operation identity and any provider call correlation before treating a timeout as retryable. The timeout establishes that this waiter stopped receiving a result; it does not establish that no billable call leg exists. I would use only the provider's documented reconciliation and idempotency contract. If the supported evidence cannot resolve the possible call, the application retains unknown rather than silently dialing again through another trunk.

Admission should bound both call-start rate and live call concurrency, with separate budgets for control and observation. A timed-out waiter must not free a slot while a known physical call is still active. Calling policy, suppression, destination and current permission must be checked for a genuinely new attempt. I would test response loss after dialing, delayed answer, a process restart and a later cancellation request. These are proposed phone scenarios: they transfer lessons from P2 provider operations, not a claim that the POC's fake-SMS retry contract applies to SIP carriers.

Is exponential backoff enough to make the retry safe?

It reduces retry pressure but does not establish nonacceptance. First decide whether another external call is permitted under the original operation's contract; only then choose bounded timing, jitter, current permission and carrier-capacity policy.

What should be counted as success?

Track request admission, provider call creation, ringing, answer and application completion separately. A voicemail or IVR can answer a call. A transport-level result must not be presented as a verified human conversation or completed business task.

REC-P1-04 · Separate interruption onset from recovery — OPTIONAL / MERGE

An agent stops speaking on background noise and later resumes. Which controls would you inspect, and what must business work do?

Inspect the actual turn/interruption mode, VAD quality, onset minimum duration/word thresholds and adaptive detector observations. false_interruption_timeout is not a delay before stopping speech: it governs silence after an interruption, when the framework can identify a false interruption and resume without user transcription. In this pin the activity can pause output before this recovery decision. A short stop can be a real command, while a longer acknowledgment can still be feedback, so use labeled representative audio. Preserve the accepted P1/P2 operation and output observations. Interruption stops or pauses conversation output; business cancellation requires its own explicit policy and cannot erase a possible external effect.

Should increasing the recovery timeout prevent the initial cutoff?

No. It changes how long recovery waits after the interruption. To address onset false positives, inspect the selected audio signal and onset/adaptive controls, then measure cutoff and resume behavior separately.

How would you evaluate the setting?

Label intended stops, backchannels, noise and silence across languages and environments. Measure false interruption, missed interruption, output stop/resume latency and user task outcomes; word count alone is not ground truth.
